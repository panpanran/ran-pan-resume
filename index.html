Max AI Learning

Max AI Learning is an intelligent learning platform supporting multi-subject, multi-grade, personalized practice and diagnostics. Live site: https://maxaionline.org/

Features

  • React frontend (Vite) + Express backend (JWT, OpenAI)
  • Chinese/English switching (i18next)
  • Grade/subject selection with saved preferences
  • Pinecone vector retrieval, mistake notebook, targeted practice
  • Multi-agent question generation (plan → generate → dedupe → evaluate/refine)
  • Live generation progress bar for diagnostic and knowledge-point practice
  • Quality feedback loop (Ragas/judge scores → feedback store + prompt patches)
  • Build-time version badge (vYYYY.MMDD.HHmm) so each Render deploy is visible in the UI
  • SPA deep links (/app, /scores, …) with session redirect back to login when logged out

Quick Start (Local)

1. Install dependencies

# Backend
cd backend
npm install

# Frontend
cd ../frontend
npm install

2. Configure environment variables

Copy .env.example to .env and fill in:

JWT_SECRET=your_jwt_secret
OPENAI_API_KEY=(optional, for OpenAI 4.1)

3. Start services

# Backend
cd backend
npm run dev

# Frontend
cd ../frontend
npm run dev

Access frontend: http://localhost:5173

Deployment

Production on Render.com (frontend static + backend web service), Postgres on Neon (neondb), vectors on Pinecone index ai-learning. Pushing to GitHub master auto-deploys. See the project README for service IDs and publish steps.

Question Generation Algorithm

The diagnostic question generation runs as a multi-agent pipeline in agents/app (entry point orchestrators/diagnostic_run.py): plan → generate → dedupe → evaluate/refine → persist.

Steps

  1. Receive request (DiagnosticRunRequest)
    • Inputs: language lang, question count num_questions, student_profile, knowledge point list `kp_list`, grade/difficulty grade_guidance, retrieval_snippets, feedback_context, and more.
    • The question count is clamped to 1–20 (num = max(1, min(20, num_questions))).
  2. Knowledge-point planning (agents/planner.py → build_knowledge_point_ids_plan)
    • Optional: when use_db_planner is enabled, per-KP historical usage counts kp_usage_counts are read from the database.
    • Assigns a knowledge_point_id to each question slot: KPs are ordered by ascending usage count plus a random tiebreaker, prioritizing less-used knowledge points; when there aren't enough KPs, slots are filled by randomly sampling from the top third of the pool.
    • Produces two plans: the final plan (length num) and an over-generation gen_plan (length num + 5).
  3. LLM generation (agents/generator.py → generate_mcq_batch)
    • Uses prompts/diagnostic.py to build the system and user prompts, injecting the student profile, knowledge points, assignment plan, retrieval snippets, metadata to avoid, and past feedback.
    • Calls OpenAI (default gpt-4.1-mini, temperature=0.2, JSON output mode), requiring strict JSON {lesson, questions}.
    • Over-generates num + 5 questions to improve the yield of usable items.
  4. Parse & normalize (generator.py → _parse_json, _normalize_question)
    • Parses the model's JSON output (falls back to extracting the outermost braces on error).
    • Normalizes each question's fields (_coerce_question_shape) and validates it: type must be mcq; exactly 4 options in each language; answer_cn/answer_en must appear in the corresponding options; otherwise the item is dropped.
    • Backfills knowledge_point_id from the plan (falling back to fallback_kp_id if it is not in the allowed set).
  5. Deduplication (workers/dedupe.py → dedupe_questions)
    • Computes a content_options_hash per question: a SHA-256 over the normalized English content and options.
    • Removes duplicates within the batch first, then compares against existing database hashes db_hashes (queried when check_db_hashes is enabled).
    • Keeps the first num accepted questions; if too few are accepted, falls back to the raw questions to fill the gap.
  6. Quality evaluation & refinement (orchestrators/diagnostic.py, LangGraph: evaluate → critic → (refine loop))
    • evaluate (evaluators/quality.py):
      • Rule checks (rules.py): valid schema, answer present in options, single correct answer, KP assigned, matches the plan, metadata present, bilingual fields complete.
      • LLM judge (judge.py): kp_alignment (fit to the knowledge point), explanation_support (whether the explanation supports the answer), distractor_quality.
    • critic (agents/critic.py): when scores fall below the thresholds in config.py (e.g. kp_alignment < 0.7, distractor_quality < 0.6) or rules fail, produces a critique and rewrite instructions.
    • route: if refinement is enabled, max_refine_rounds (default 2) has not been exceeded, and questions still need fixing, go to refine; otherwise finish.
    • refine (agents/refiner.py): failing questions are rewritten one by one by the LLM according to the critique, then sent back to evaluate for re-scoring.
  7. Persist (optional) (workers/persist.py → persist_question)
    • When persist is set and grade_id/subject_id are provided, each question's hash is recomputed and it is written to the database, with the generated id backfilled.
  8. Return response (DiagnosticRunResponse)
    • Includes run_id, status, the KP plan and rationale, lesson, the final questions, batch quality metrics and per-question scores, refine rounds, dedupe rejection count, and the list of persisted ids.

Fast OCR

FastOcr is an intelligent extraction service for LTSS Plan of Service (POS) documents: upload PDF/images → OCR/text parsing → LLM structured persistence → build a FHIR R4 Bundle → (optionally) push to Fast EMR. Live site: https://ranonline.org/

Stack: FastAPI + MongoDB + Redis/Arq + OpenAI/LangGraph + FHIR R4 HTTP.

End-to-end data flow (PDF → OCR → DB → Fast EMR / FHIR)

The pipeline is not a single automatic request. It runs as three stages (the Web UI chains the first two; FHIR export is triggered separately).

[Upload PDF/image]
      │
      ▼
 POST /ingest/file  (or /ingest/pdf)
      │  Create doc_id, save file under data/uploads/
      │  Mongo: ingest_jobs + ocr_docs
      │  Enqueue Arq: ingest_document / ingest_pdf
      ▼
[Worker parse]
      │  PDF: PyMuPDF / pdfplumber (full-page Tesseract OCR off by default)
      │  Images: Tesseract OCR
      │  Mongo: ocr_results  ← raw_text + meta (e.g. goals_table)
      ▼
 POST /ocr/run   (or GET /ocr/stream)
      │  LangGraph: planner → retrieve → reason → execute
      │  LLM extracts PosDocument
      │  Mongo: pos_docs  ← structured clinical / service data
      ▼
 POST /fhir/export/{doc_id}?mode=push
      │  Read pos_docs + original PDF
      │  Build FHIR R4 batch Bundle
      │    Patient / Binary(PDF) / DocumentReference / CarePlan / Goal[]
      │  HTTP POST → Fast EMR FHIR base URL (FHIR_BASE_URL)
      │  Write back pos_docs.fhir_export
      ▼
[Fast EMR]  Stores FHIR resources for EMR / downstream consumers

1. Upload PDF / image

  • Entry: Web UI or API POST /ingest/file / POST /ingest/pdf
  • Behavior: Create doc_id; store file under data/uploads/; write Mongo ingest_jobs and ocr_docs; enqueue parse job on Redis/Arq
  • Poll: GET /ingest/{ingest_id} for queued / running / success / failed

2. PDF / image processing and OCR → raw text

  • Worker: Arq worker must run alongside the API
  • PDF: extract text first; table goals go into meta.goals_table. Full-page OCR is off by default (scanned PDFs need enable_ocr=True)
  • Images: Tesseract OCR to text
  • Persist: Mongo ocr_results (ocr.raw_text, pages, meta)
  • Side path: optional outbox JSONL / S3 export (this is not Fast EMR)

3. LLM structured extraction → database

  • Trigger: POST /ocr/run or GET /ocr/stream?doc_id=
  • Graph: planner → retrieve → reason → execute → OpenAI → PosDocument → save_pos_doc
  • Persist: Mongo pos_docs (members, goals, service hours, etc.)
  • Query: GET /pos, GET /pos/by-doc/{doc_id}

4. Data handoff to Fast EMR (FHIR)

Fast EMR is the configured FHIR R4 HTTP server (typically the Fast EMR site on Azure), not a separate SDK.

  • Trigger: POST /fhir/export/{doc_id}?mode=bundle_only|push
  • Bundle: Patient, Binary (PDF base64), DocumentReference, CarePlan, Goal[]
  • Push: HTTP POST to FHIR_BASE_URL (Fast EMR); optional Bearer token
  • Write-back: export summary on pos_docs.fhir_export

Shortest operator path: start Mongo + Redis + API + Arq worker → upload POS PDF → wait ingest success → POST /ocr/run → POST /fhir/export/{doc_id}?mode=push.

Main Mongo collections

  • ingest_jobs — upload job status
  • ocr_docs — uploaded file path and metadata
  • ocr_results — OCR/parsed raw text and page meta
  • pos_docs — structured POS from the LLM + optional fhir_export
  • outbox_events — side-channel OCR export (JSONL/S3), not EMR

Key APIs

  • POST /ingest/file — upload PDF/image and enqueue parse
  • GET /ingest/{ingest_id} — parse job status
  • POST /ocr/run — LangGraph structured extraction
  • GET /pos, GET /pos/by-doc/{doc_id} — read structured POS
  • POST /fhir/export/{doc_id} — build / push FHIR Bundle
  • GET /health, /metrics — health and monitoring

Run locally

Requires MongoDB, Redis, and an OpenAI API key. Configure FHIR_BASE_URL when pushing to EMR.

uv sync --dev
uv run uvicorn app.main:app --reload --port 8000
uv run arq app.workers.worker.WorkerSettings

Open http://localhost:8000/ for the upload/analyze UI. Production: https://ranonline.org/

Known limitations

  • Ingest does not automatically call the LLM or FHIR; /ocr/run and /fhir/export are separate steps.
  • PDF workers default to enable_ocr=False; pure scans may need OCR enabled.
  • Outbox → JSONL/S3 is not the same as pushing to Fast EMR.
